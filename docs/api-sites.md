# Список майданчиків: фільтри й пагінація

Частина Z2 першого чекпоінта, issue #6; перевірка власника пов'язана з #8.
Контракт формується в `/openapi/v1.json`
з `SiteQuery`, `PagedResult<SiteDto>` і відповідей контролера. Тест `SitesApiTests`
перевіряє наявність параметрів, схему сторінки й відповідь 400 у справжньому OpenAPI.

## Запит

`GET /api/sites?page=1&pageSize=20&name=Ліс&minLatitude=49&maxLatitude=51`

| Параметр | Поведінка |
|---|---|
| `page` | Ціле число від 1, типово 1. Сторінка за межами вибірки повертає 200 і порожній `items`. |
| `pageSize` | Додатне ціле число, типово 20. Значення понад 100 обмежується до 100 без помилки (кейс 21). |
| `name` | До 100 символів. Пошук буквального фрагмента з урахуванням регістру; пробіли по краях відкидаються. `%` і `_` не є шаблонами. Порожнє значення не фільтрує. |
| `minLatitude`, `maxLatitude` | Необов'язкові включні межі від −90 до 90. |
| `minLongitude`, `maxLongitude` | Необов'язкові включні межі від −180 до 180. |

Фільтри поєднуються через AND. Мінімальна межа не може перевищувати максимальну.
Некоректні числа, нульові/від'ємні `page` і `pageSize`, `NaN`, нескінченність та
некоректні діапазони дають 400 `ValidationProblemDetails` до звернення до бази.

Порядок — назва, потім `Id`: однакові назви не спричиняють довільного переставлення
між сторінками. Фільтрація, підрахунок і вибірка сторінки виконуються через LINQ у БД.
Колекція повністю в пам'ять не завантажується. Порядок назв залежить від collation СУБД.
Пагінація не є знімком: паралельне додавання/видалення записів може змінити наступні сторінки.

## Відповідь і зміна контракту

Раніше `GET /api/sites` повертав масив. Тепер відповідь 200 є об'єктом:

```json
{
  "items": [],
  "totalCount": 0,
  "page": 1,
  "pageSize": 20
}
```

`totalCount` рахується після фільтрів, до пагінації. `pageSize` містить фактичний,
уже обмежений розмір. Для великого номера сторінки немає переповнення зміщення.
Клієнтам API потрібно читати `items` і запитувати наступні сторінки; це зміна публічного
контракту, яку має переглянути Z4. Локальний MAUI-сервіс читає власний `LabDbContext`
і не використовує цей HTTP-контракт.

## Власність і оновлення

`GET /api/sites` повертає лише майданчики з `OwnerId`, що збігається з перевіреним
`sub` поточного користувача. Читання чужого або legacy-майданчика без підтвердженого
власника через `GET /api/sites/{id}` дає 404. `POST /api/sites` сам встановлює
`OwnerId` із поточного користувача; тіло запиту не може призначити власника.

`PUT /api/sites/{id}` приймає повний `UpdateSiteRequest` з назвою та координатами.
Усі три поля (`name`, `latitude`, `longitude`) обов'язкові. Пропущена координата
або `null` дає 400 `ValidationProblemDetails`, а не підставляє нуль і не змінює
збережений запис. Явні координати 0 допустимі. Назва після Trim має 3–100 символів.
Успішне оновлення повертає 204; чужий або безвласний наявний майданчик дає 403,
відсутній — 404, некоректні дані — 400. Власника й `CreatedAt` змінити не можна.
Відмова сервісу через власність повертає 403 `ProblemDetails` з типом
`application/problem+json`, як задекларовано в OpenAPI; ім'я власника не розкривається.
Перевірка власності виконується в `SiteService`, а не лише в контролері.
Це змінює публічний контракт Z2 і потребує рев'ю власника Z2; схема БД не змінюється.

Звуження контракту Z2 від 18.10.2026: клієнт має завжди передавати обидві координати
при PUT. Відсутні поля не означають часткове оновлення. Перевірки —
`SiteUpdateContractTests`: JSON без полів/із null, невалідна назва, збереження даних
після відмови, 403/404/401, явні нулі та required-поля OpenAPI.

Instrument, Experiment, виміри, статистика та інші правила доступу залишаються своїм
наступним задачам; цей етап не закриває весь issue #6.
