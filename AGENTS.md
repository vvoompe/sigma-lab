# AGENTS.md - правила роботи над STEM-проєктом «Польова лабораторія»

> Цей файл - **єдиний контракт для людей і ШІ-агентів** у цьому репозиторії.
> Агент (Codex, Claude Code, Cursor, будь-який інший асистент) зобов'язаний прочитати його
> перед першою зміною в коді. Людина - теж: тут зафіксовані домовленості, які не
> переглядаються на ходу (хіба що через issue і PR, і тоді файл оновлюється).

**Дисципліна:** Мультиплатформне програмування (кафедра ПСТ, КНУ ім. Тараса Шевченка)
**Формат:** командний STEM-проєкт, 4 учасники, усі працюють з ШІ-агентами
**Оцінювання:** командна частина 30 % (якість продукту), індивідуальна 70 % (процес, зона
відповідальності, складність зони, захист). Поріг зарахування - **60 %**. Множник
доброчесності M: 1,0 без порушень, 0,5 за недекларований ШІ або плагіат, **0,0 за видавання
чужої роботи за власну**.

---

## 0. Правило номер один

**Вайбкодити можна, «пофіг» - ні.** Оцінка тут індивідуальна: у документі кафедри прямо
описано команду, де продукт добрий, а один учасник отримує 47 % і проєкт йому не
зараховують. Тебе рятує не те, що агент написав код, а те, що:

1. у тебе є **своя зона**, зафіксована на старті, з рівнем складності;
2. ти **розумієш** свій код і можеш пояснити його без підказок (E1, E2 - це 0,17 із 0,70);
3. у git видно **процес**: issue → гілка → PR → рев'ю → merge (A1, A2, B1, B2, B3 - 0,36).

Тому кожен учасник зобов'язаний уміти відповісти на три питання про будь-який свій рядок:
**що він робить, чому саме так, і що зламається, якщо його прибрати.**

## 1. Продукт

**Польова лабораторія** - система збору, обробки та аналізу вимірювань.

Дослідницька група проводить вимірювання (фізика, хімія, екологія - будь-яка польова
методика), вносить їх у мобільному застосунку **навіть без мережі**, після появи зв'язку дані
синхронізуються із сервером, система рахує статистику й похибки, тримає серії вимірювань і
порівнює їх з еталоном.

**STEM-ядро (те, що робить це STEM-проєктом, а не черговим CRUD):**

- метрологія: середнє, СКО, стандартна похибка, довірчий інтервал, похибка приладу;
- чисельні методи: лінійна регресія, апроксимація, виявлення викидів (правило 3σ), інтерполяція;
- обробка даних: агрегація серій, порівняння з еталоном у межах заданої похибки.

**Багатоплатформність (вимога дисципліни):** клієнт .NET MAUI (Android + десктоп) → REST API
→ фоновий обробник → контейнеризація Docker.

### 1.1. Доменні сутності (базові, далі - тільки через issue)

| Сутність | Роль у системі | Ключові поля |
|---|---|---|
| `User` | учасник (дослідник / керівник лабораторії / адміністратор) | `Email` (унікальний), `Role`, `PasswordHash` |
| `Site` | точка відбору / майданчик | `Name`, `Latitude`, `Longitude`, `OwnerId` |
| `Instrument` | прилад (модель, похибка) | `Name`, `SerialNumber` (унікальний), `AccuracyValue`, `AccuracyUnit` |
| `Experiment` | серія вимірювань (підписана після завершення) | `Title`, `SiteId`, `InstrumentId`, `Status`, `StartedAt`, `SignedAt` |
| `Measurement` | одне вимірювання в серії | `ExperimentId`, `Value`, `Unit`, `MeasuredAt`, `AuthorId`, `ClientId` (UUID для офлайн-синхронізації) |
| `ReferenceValue` | еталон для порівняння | `ExperimentId`, `Expected`, `Tolerance` |

**Інваріанти, які не можна порушити (їх перевіряють тести):**

1. `Measurement` можна додати лише в `Experiment` зі статусом `Draft`; підписану серію не змінюють.
2. `Measurement.Value` мусить бути в межах діапазону приладу - інакше 400 з поясненням.
3. `ClientId` унікальний: повторна синхронізація того самого вимірювання не створює дубль.
4. Обчислені статистики не зберігаються як «істина», вони перераховуються (крім кешу).

## 4. Правила коду

- **Сирий SQL заборонений.** Тільки LINQ/EF Core. Якщо без SQL не обійтись - це окремий issue
  з обґрунтуванням, сирий SQL дозволений лише на читання і тільки через `FromSql` з
  параметрами. Запис сирим SQL - заборонено завжди.
- **Ніяких секретів у репозиторії.** Паролі, JWT-ключі, рядки підключення з паролями - тільки
  змінні середовища або Secret Manager. У файлах - `.env.example` із заглушками.
- **Ніяких TODO і заглушок у merge.** Якщо робота не завершена - гілка не мержиться.
- **`async/await` до кінця.** Ніяких `.Result` і `.Wait()`; якщо метод виконує I/O - він async.
- **Nullable увімкнений.** `string?` - це сигнал, що значення може не бути. Не «глушити»
  попередження `!`, а обробляти випадок.
- **Попередження - це помилка.** `TreatWarningsAsErrors=true` у `Directory.Build.props`.
  Згенерований EF-код міграцій виключається з аналізу через `<NoWarn>` у відповідному
  `.csproj`, а не через вимкнення аналізаторів у всьому solution.
- **Одна відповідальність на клас.** Сервіс не читає `HttpContext`; контролер не торкається
  `DbContext`; домен не знає про базу.

## 5. Правила даних

- **3 нормальна форма**; денормалізація - тільки з поясненням у `docs/decisions-log.md`.
- **PK/FK на кожному зв'язку** + явна політика видалення (`Cascade` / `Restrict` / `SetNull`) з
  обґрунтуванням у Fluent-конфігурації.
- **Індекси** на всіх полях фільтрації, сортування та JOIN: `ExperimentId`, `MeasuredAt`,
  `Status`, `SiteId`, `ClientId` (унікальний).
- **Транзакції** там, де змінюється більше однієї сутності (наприклад, підпис серії + перерахунок).
- **Міграції - версія схеми**, а не `EnsureCreated`. Нові проєкти міграцій обов'язково
  отримують пакет `Microsoft.EntityFrameworkCore.Design` і власну `*DesignTimeDbContextFactory`,
  інакше `dotnet ef` у них не запуститься.
- **Дві СУБД - дві міграції на кожну зміну моделі.** Одна зміна моделі = два `migrations add`
  + два `database update`.

---

## 6. Правила API

- **Контракт спершу.** Будь-який новий ендпойнт починається з DTO в `Lab.Contracts` і issue, а
  не з контролера.
- Коди відповідей: `200/201/204` успіх, `400` валідація, `401` не автентифікований, `403`
  автентифікований але без прав, `404` нема ресурсу **або** він не твій у публічних сценаріях,
  `409` конфлікт (дубль `ClientId`/`SerialNumber`).
- Помилки - у форматі `ProblemDetails` з єдиним обробником; трасування стеку назовні немає.
- Пагінація обов'язкова для колекцій, максимальний `pageSize` обмежений.
- `/openapi/v1.json` оновлюється разом із кодом: якщо змінився ендпойнт - у PR є новий опис.
- Розрахункові ендпойнти повертають числа **плюс** похибку й одиниці виміру; «просто число» у
  відповіді - ознака недоробленого контракту.

---

## 7. Правила безпеки

- JWT: підпис HS256, ключ **тільки** зі змінної середовища, час життя обмежений, `ClockSkew = 0`.
- Ролі: `Researcher` (свої серії), `LabManager` (усі серії свого майданчика + підпис),
  `Administrator` (керування користувачами й приладами).
- **Володіння ресурсом** перевіряється в сервісному шарі, а не «декоратором зверху»: чужий
  ресурс не редагується (403 замість тихого 200).
- Пароль: хешування з сіллю (PBKDF2/Identity-хешер), мінімальна політика довжини; повідомлення
  про невдалий вхід однакове для «нема користувача» і «невірний пароль».
- Аудит: підпис серії, зміна ролі й видалення серії пишуться в журнал (хто, коли, що).

## 8. Правила клієнта й синхронізації

- Локальна база клієнта - SQLite, **та сама доменна модель**, ті самі сервісні інтерфейси.
- Кожен вимір отримує `ClientId` (UUID) на пристрої - він і є ключем ідемпотентності при синхронізації.
- Черга синхронізації: операція має стан `Pending / Sent / Failed`; повторна відправка не створює дубль.
- Конфлікти: версія запису (`RowVersion`/`UpdatedAt`); політика - документована й покрита тестами,
  а не «якось вирішимо».
- Офлайн-режим - обов'язковий: застосунок має працювати без мережі і показувати стан синхронізації.

## 9. Git: обов'язкова дисципліна процесу

Це не формальність - за це дають 0,36 із 0,70 індивідуальної частини.

**Робочий цикл на кожну задачу:**

1. `issue` з описом, критеріями приймання та оцінкою складності (S/M/L).
2. Гілка від `main`: `feature/<номер-issue>-<коротка-назва>`, `fix/...`, `docs/...`, `test/...`.
3. Код + тести в одному PR. **Прямі коміти в `main` заборонені.**
4. PR з описом за шаблоном (розділ 11), мінімум **один рев'ю іншим учасником**.
5. Рев'ю знаходить суттєву проблему **або** пропонує обґрунтоване покращення - саме такі
   рев'ю зараховуються (потрібно ≥3 результативних на семестр).
6. Merge тільки після зеленого CI.

**Коміти:** `<тип>(<область>): <що зроблено>` - `feat`, `fix`, `test`, `docs`, `refactor`,
`chore`, `perf`. Приклад: `feat(measurements): відхиляти значення поза діапазоном приладу`.
Один коміт - одна думка. Повідомлення українською, без «fix», «wip», «asdf».

**Гігієна:** ≥1 змістовний коміт на тиждень від кожного; кожен PR прив'язаний до issue;
гілки видаляються після merge; force-push у `main` заборонений завжди.

### 10.1. Чому рівні саме такі (це аргументи для захисту, не прикраси)

- **Z1 - експертний.** Не через «багато коду», а через те, що тут немає готових шаблонів:
  дві СУБД з різною поведінкою (типи колонок, порядок `NULL`, підтримка `DateTimeOffset`), модель,
  яка мусить тримати інваріанти, і розрахункове ядро з оцінкою похибки. Складність доводиться не
  словами, а тестами на еталонних значеннях.
- **Z3 - експертний.** Рубрика кафедри прямо називає експертним рівнем «складну авторизацію».
  Тут вона справді складна: три ролі, політики, володіння ресурсом у сервісному шарі, аудит
  підпису серій, і все це мусить не пропускати чужий ресурс і не віддавати трасування назовні.
- **Z4 - експертний.** Рубрика називає експертним рівнем «розподілені воркери». У нас це офлайн-клієнт
  із чергою синхронізації та розв'язанням конфліктів: найскладніша логіка проєкту і найдовші тести.
- **Z2 - просунутий (0,9), і це свідомо.** CRUD із валідацією та пагінацією - це просунутий рівень, а
  не експертний. Якщо заявити тут 1,0 без зміни змісту, на захисті почнуть питати як з експерта, і
  D1 рахується як **складність × повнота** - тобто завищена складність без відповідного змісту дає
  не «плюс», а втрату.

**Щоб Z2 став експертним чесно**, у зону треба додати складні задачі, і тоді рівень буде
обґрунтованим. Мінімум дві з трьох:

1. **Ідемпотентність мутацій** - `Idempotency-Key` для POST і повторна відповідь без дубля.
2. **Масові операції з частковими помилками** - пакетна синхронізація з відповіддю `207 Multi-Status`
   і звітом по кожному елементу.
3. **Стрімінговий експорт** великих серій (CSV/JSON) без завантаження всього в пам'ять + контрактні
   тести, які перевіряють відповідність OpenAPI фактичним відповідям.

Це не «папірці для декларації»: 1 і 2 прямо потрібні системі (синхронізація з клієнта і масове
внесення вимірів), а 3 закриває польову специфіку - серії бувають на тисячі вимірів.

## 12. Визначення готовності (Definition of Done)

Задача вважається готовою, коли **усе** виконано:

- [ ] код збирається без попереджень (`dotnet build -c Release`: 0 Warning, 0 Error);

## 17. Пастки, на які вже наступали (не повторювати)

1. **`dotnet` не знайдено / EF не бачить рантайм.** Тримайте `DOTNET_ROOT` як Windows-шлях
   (`C:/Users/<user>/.dotnet`), а в `PATH` - MSYS-форму (`/c/Users/<user>/.dotnet`); інакше
   bash ріже `PATH` по двокрапці й `dotnet` зникає (exit 127).
2. **Два набори міграцій в одній assembly конкурують за `ModelSnapshot`.** Тримайте окремі
   проєкти міграцій і окремі `*DesignTimeDbContextFactory`.
3. **Новий проєкт міграцій без пакета `EntityFrameworkCore.Design`** - `dotnet ef` падає з
   «doesn't reference Design». Пакет + фабрика обов'язкові.
4. **SQLite не вміє сортувати й агрегувати `DateTimeOffset`.** Для дат використовуйте
   `DateTime` в UTC; для клієнтських операцій з часом - документуйте рішення.
5. **Порядок `NULL` у сортуванні різний** (SQLite - NULL першими, PostgreSQL - останніми).
   Тести сортування мусять це враховувати, інакше «однаковий результат» на двох СУБД - міф.
6. **Згенерований код міграцій валить аналізатори.** Виключайте `Migrations/*.Designer.cs` і
   `*ModelSnapshot.cs` через `<NoWarn>`, а не вимикайте аналіз глобально.
7. **Кирилиця ламається в PowerShell 5.1 і в inline-рядках curl.** Файли `--data-binary @файл`
   у UTF-8; шляхи й тіла запитів - без кирилиці в командному рядку.
8. **Шляхи в git-bash** (`/c/...`) не працюють як рядок підключення до SQLite всередині
   застосунку - там потрібен Windows-шлях (`C:/...`).
9. **Кириличні імена файлів у скриптах.** `git ls-files` екранує їх octal-послідовностями -
   використовуйте `git ls-files -z`.
10. **`MPP_DB_PROVIDER=1 dotnet test`** як префікс змінної іноді виставляється не тому процесу,
    якщо команда складена з `export` у тому ж рядку. Пишіть `VAR=1 dotnet test`, без `export`.
