# Декларування використання ШІ (META-USAGE)

**Проєкт:** STEM-проєкт «Польова лабораторія», дисципліна «Мультиплатформне програмування».
**Команда:** Саша (Z1 - дані й математика), Артем (Z2 - контракти, API, CI), Ваня (Z3 - безпека
й доступ), Юра (Z4 - клієнт і синхронізація).

Цей файл - **обов'язковий артефакт** за правилами кафедри ПСТ. Використання ШІ дозволене за
трьох умов: (1) декларування, (2) володіння матеріалом на захисті, (3) розуміння згенерованого
контенту. Множник доброчесності: **M = 1,0** без порушень, **M = 0,5** за недеклароване
використання або плагіат, **M = 0,0 і комісія** за видавання чужої роботи за власну.

> **Правило ведення.** Кожен учасник заповнює **свій** розділ і оновлює його під час роботи,
> а не в кінці семестру. Записи мають бути фактами: що саме просили, що отримали, як
> перевірили, що довелося виправити руками.

---

## 1. Як ми працюємо з ШІ (спільне)

- **Інструменти:** кожен учасник використовує свій асистент (агент для розробки з доступом до
  файлів і терміналу). Конкретні назви продуктів і моделей учасники зазначають у своїх розділах
  за бажанням; принципово тут те, що код і тексти генеруються ШІ під контролем людини.
- **Межа відповідальності:** ШІ пише код і тексти; людина ухвалює рішення, перевіряє результат
  і відповідає за нього. Незрозумілий фрагмент не мержиться.
- **Обов'язкова перевірка:** після кожної зміни запускається `dotnet build -c Release` (нуль
  попереджень) і `dotnet test`; вивід додається в опис PR. Покриття перевіряється скриптом
  `scripts/coverage-summary.py`.
- **Що заборонено:** приймати результат без перевірки; лишати `TODO` і заглушки; підправляти
  тести, щоб збірка стала зеленою; вставляти секрети в код.

## 2. Саша - зона Z1 (дані, схема, розрахункове ядро)

**Інструменти поточного інкременту #5.** Модель OpenAI `gpt-6.1-sol` через API,
агентний режим із доступом до локальних файлів, терміналу й читання GitHub.
MathNet.Numerics 5.0.0 (MIT) - бібліотека для квантили Student t.

**Ключові запити.**

| # | Що просив | Що отримав | Як перевірив |
|---|---|---|---|
| 1 | Аудит репо та вимог МПП без змін | Аналіз коду, CI, milestones, офіційних вимог і PDF захисту | Прочитано першоджерела та справжні логи GitHub Actions |
| 2 | Почати Z1 і проганяти кластер тестів між частинами | Чисте математичне ядро #5, тести, пояснення меж | Відтворено відсутню поведінку й чисельні помилки до виправлень; цільові тести та регресія solution з окремою PostgreSQL |

**Що згенеровано в цьому інкременті.** `src/Lab.Application/Statistics/`,
`SeriesStatisticsTests.cs`, `MeasurementAnalysisTests.cs`, `LinearRegressionTests.cs`,
`docs/statistics-core.md`, запис логу рішень і ця декларація. У `.csproj` додано
MathNet.Numerics. Саме на етапі #5 модель БД, DTO, API та MAUI не змінювалися;
подальші зміни моделі #3/#4 описано нижче окремо.

**Що перевірено на живих прогонах.** Release build, математичні тести,
регресія solution без PostgreSQL та з ізольованою PostgreSQL 15, звіт coverlet.
Остаточні числа й область покриття наводяться у звіті перевірок. Локальний PASS
не означає опублікований PR або успішний CI цієї гілки. Тести відтворили втрату
дисперсії через underflow та хибний прогноз із непредставним середнім x до виправлення.

**Що довелося виправити руками.** Ручні зміни користувача на цьому етапі не зафіксовані.
Агент виправив чисельні крайові випадки після тестів. Розуміння й особисту адаптацію
Саша підтверджує окремо; автоматичні тести не є доказом володіння матеріалом.
Попередній каркас також створювався з допомогою ШІ; його точні інструменти та внесок
потрібно відновити з історії окремо, цей запис їх не підміняє.

**Мікрозміни для підготовки, ще не виконані Сашею на захисті.**
1. Змінити рівень довіри й пояснити ширину інтервалу.
2. Змінити поріг викидів або допуск і додати граничний тест.

**Наступний інкремент #3/#4.** Та сама модель OpenAI `gpt-6.1-sol` через API,
локальні файли, термінал, читання GitHub та незалежне агентне review. Згенеровано
User/Instrument/ReferenceValue/Experiment/Measurement, їхні Fluent-конфігурації,
дві нові міграції на кожну СУБД, тести й `docs/data-model.md`.
Саша явно погодив мінімальний профіль User без auth і один прилад/одиницю на серію.
Site.OwnerId став nullable FK; старі значення збережено в LegacyOwnerId без
фіктивних користувачів. Існуючі тести з OwnerId=42 отримали реальний профіль у
fixture; перевірка власника не видалена. Тест історії міграцій очікує фактичні
три кроки замість старого одного. Згенерований Down спочатку падав на SQLite FK;
після відтворення дефекту міграцію SiteOwnership виділено окремо.
Реальні прогони включають SQLite і тимчасову PostgreSQL 15, міграції в обидва
боки, збереження старих даних, UNIQUE/FK та concurrency. Детальний результат
рев'ю та фінальні числа - у звіті перевірок. Паролі, JWT, ролі, API та синхронізація
не реалізовані. Ручних правок користувача не зафіксовано; розуміння коду потрібно
підтвердити окремо, а не підміняти зеленими автотестами.

## 6. Порівняння підходів (питання на захисті)

Кафедра окремо просить уміти **аргументовано порівняти** обрану стратегію застосування ШІ з
альтернативами. Нижче - каркас, який команда доповнює своїми аргументами.

| Підхід | Переваги | Обмеження в нашому проєкті |
|---|---|---|
| Генерація агентом із доступом до терміналу | швидкий цикл «зміна → збірка → тести», видно реальний вивід | агент схильний пропонувати звичні шаблони (наприклад, один набір міграцій на дві СУБД) |
| Чат-асистент без доступу до файлів | швидкі відповіді на теоретичні питання | не перевіряє, що код справді збирається; результат треба переносити руками |
| Написати самому з документацією | глибше розуміння, немає залежності від інструмента | повільніше на рутині (тести, DTO, конфігурації) |
| Копіювання готового рішення з мережі | швидко | пряме порушення доброчесності: M = 0,5 і вище |
