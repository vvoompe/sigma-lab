# Модель даних Z1 із доповненням Z3 - issues #3, #4 та #8

Модель і міграції передаються разом; локальна перевірка не заміняє review та CI.
Профіль користувача лишається мінімальним, а облікові дані й аудит автентифікації
додаються окремими таблицями Z3. Перевірки власника серії, підпис і решта HTTP CRUD
та синхронізації не є частиною цієї моделі.

## Узгоджені із Сашею контракти

- User - мінімальний профіль із `int Id`, іменем та email; без паролів, ролей і JWT.
- UserCredential - облікові дані 1:1 з User; хеш, роль, лічильник помилок та lockout.
- AuditEntry - незмінна подія з актором, типом/ідентифікатором цілі та UTC-часом.
- Одна Experiment - один Instrument та одна одиниця вимірювання.
- Unit зберігається в Instrument, а не повторюється в кожному Measurement.
- ClientId - непорожній UUID, унікальний глобально для Measurement.
- Version - додатний `long`, змінюється прикладним кодом, EF перевіряє його як concurrency token.

Ці контракти ще потрібно передати власникам Z2/Z3/Z4 на командне review.

## Таблиці та зв'язки

| Таблиця | Призначення | Зовнішні ключі |
|---|---|---|
| lab_users | Профіль користувача | Немає |
| user_credentials | Хеш пароля, роль і стан блокування | UserId -> lab_users (спільний PK/FK) |
| audit_entries | Події безпеки та зміни ролей | ActorId -> lab_users |
| sites | Майданчик | OwnerId -> lab_users (автор), ManagerId -> lab_users (керівник), обидва nullable |
| instruments | Прилад і метрологічні параметри | OwnerId -> lab_users |
| reference_values | Іменований еталон: Unit, Value, AbsoluteTolerance | Немає |
| experiments | Серія, її власник, стан та підпис | SiteId -> sites; OwnerId/SignedById -> lab_users; InstrumentId -> instruments; ReferenceValueId -> reference_values |
| measurements | Число, UTC-час, UUID клієнта та версія | ExperimentId -> experiments |

PK профілю й доменних таблиць - `int Id`; `user_credentials.UserId` є одночасно PK і FK.
`audit_entries.Id` генерується БД. Нові числові виміри - finite double.
Еталон можна повторно використати в кількох серіях; його Unit має збігатися
з Unit приладу. Відсутній еталон дозволений.

## Нормалізація та індекси

Назва приладу, одиниця, межі й похибка не копіюються у виміри. Одиниця серії
виводиться через FK InstrumentId. Еталон - окрема сутність, не набір повторених
полів серії. Обчислені середнє/СКО/регресія в таблицях не кешуються.

NormalizedEmail - свідомо матеріалізований пошуковий ключ `Email.ToUpperInvariant()`;
Email зберігає оригінальний регістр після Trim. Конструктор встановлює обидва поля,
публічних setter немає. Унікальність перевіряється однаково на двох СУБД.

- UNIQUE: User.NormalizedEmail, Instrument.SerialNumber, Measurement.ClientId.
- Хеш і роль не зберігаються в `lab_users`; роль `Researcher` призначається при реєстрації,
  роль не приймається від клієнта. Пароль має довжину 12–128 символів; склад символів
  додатково не обмежується, хешування виконує ASP.NET `PasswordHasher<UserCredential>`.
- Після п'яти невдалих входів обліковий запис блокується на 15 хвилин. `PasswordUpdatedAt`,
  `LockoutUntil` і `OccurredAt` зберігаються як UTC.
- Подія зміни ролі й нова роль записуються одним `SaveChangesAsync`; актор має існувати,
  видалення профілю з історією аудиту обмежене FK.
- Серійний номер порівнюється з урахуванням регістру, після Trim; прихованої конвертації немає.
- Experiment: (SiteId, Status), (OwnerId, CreatedAt), індекси інших FK.
- Measurement: (ExperimentId, MeasuredAt).
- Site: збережено старі індекси; додано OwnerId і ManagerId. Один керівник на майданчик; FK з `Restrict`.

## Правила змін

- Instrument: finite min < max, finite AbsoluteError >= 0; значення на межах дозволені.
- Прилад і серія мають одного OwnerId. Це доменна узгодженість, не авторизація запиту.
- Measurement створюється через `Experiment.AddMeasurement`; список доступний лише для читання.
- `Experiment.Rename` змінює назву лише в чернетці; назва, однакова після Trim, версію не піднімає.
- `Instrument.Rename` змінює лише описову назву: серійний номер, одиниця, межі та похибка
  лишаються незмінними, інакше старі виміри втратили б сенс.
- `Measurement.Update` перевіряє чернетку, одиницю, діапазон і UTC до зміни числових полів.
- Підпис: Draft -> SignedOff, фіксуються SignedById та SignedAt. Повторний підпис,
  додавання, редагування та видалення вимірів через доменні методи відхиляються.
- Роль підписанта й доступ до майданчика перевіряє сервіс Z3; зміни ролей уже проходять
  через адміністративний сервіс із записом аудиту.
- Сервіс завантажує Instrument, а для роботи з наявними вимірами - Measurements;
  для зміни окремого Measurement також його Experiment. Незавантажену навігацію
  не можна трактувати як відсутній ресурс або порожню серію.
- Зміна виміру змінює і його Version, і Version серії. Паралельний підпис робить
  стару версію непридатною; EF повертає DbUpdateConcurrencyException.
- Один SaveChanges атомарний для змін серії та виміру. Помилка UUID або версії
  не залишає частково доданого виміру в БД.

Батьківські FK - Restrict: користувач, прилад, еталон і майданчик не видаляються
разом з історією. Experiment -> Measurement - Cascade: видалення виміру з колекції
чернетки коректно видаляє orphan у EF. Видалення підписаної серії через DbSet.Remove
та будь-які bulk-мутації мають бути заборонені/перевірені сервісом Z2/Z3;
доменні методи не є захистом від довільного обходу ORM бізнес-логіки.

## Сумісність старих Site

До появи User поле Site.OwnerId було довільним int, зокрема 0/42, без FK.
Неможливо автоматично стверджувати, що це Id реального профілю.

DomainModel перейменовує стару колонку в LegacyOwnerId без DML та без втрати значень.
Додається новий nullable OwnerId. Старі майданчики залишаються без підтвердженого
власника; вигадані профілі не створюються. Явне зіставлення з реальним User -
окрема операція власника даних/сервісу Z3, не автоматичне привласнення ресурсу.
LegacyOwnerId не використовувати для рішень про доступ. Нові виклики Site API до
інтеграції Z3 також можуть створювати майданчик без власника; це не готова безпека.

## Міграції на кожній СУБД

1. DomainModel - таблиці, індекси, інваріанти схеми й збереження LegacyOwnerId.
2. SiteOwnership - FK та індекс sites.OwnerId.
3. SecurityCredentials - окремі таблиці `user_credentials` та `audit_entries`.
4. AddSiteManager - колонка `sites.ManagerId`, FK на `lab_users` з `Restrict` та індекс; дані не змінюються.

Окрема межа потрібна для SQLite: Down спочатку завершує перебудову sites без FK,
і лише наступна Down видаляє lab_users. Інакше відкладена перебудова EF призводить
до FOREIGN KEY constraint failed. Немає ручного SQL DML чи вимикання FK кодом проєкту.
Початкові міграції не переписані.

Відкат до InitialCreate зберігає старі Site та старий ідентифікатор власника,
але прибирає нові таблиці та нові зв'язки. Це деструктивний downgrade нових даних,
не механізм резервного копіювання. Відкат до 0 видаляє також sites.

## Перевірки

- ExperimentTests / ModelValidationTests - доменні правила та відхилені зміни.
- DomainPersistenceTests - SQLite, FK, UNIQUE, UTC, orphan delete, гонка з підписом.
- DomainModelTests - реальна PostgreSQL, атомарність UUID-конфлікту, FK, UTC, concurrency;
  також upgrade -> downgrade -> upgrade старого Site на SQLite/PostgreSQL.
- MigrationLifecycleTests - latest -> 0 -> latest на обох СУБД.
- HasPendingModelChanges перевіряється для поточної моделі та відповідного snapshot.

Результати прогонів і покриття наводяться у звіті перевірок; HTTP-кейси не
позначаються виконаними лише за доменними або ORM-тестами.

## Після незалежного review

- Site.CreatedAt тепер також відновлює Kind=Utc при читанні SQLite; дефект
  відтворено червоним тестом, потім виправлено конвертером без зміни DDL.
- Редагування Measurement перевірено після повторного завантаження: число й обидві
  Version справді зберігаються в SQLite/PostgreSQL.
- Downgrade з непорожніми серіями та вимірами перевірено на обох СУБД.
- Читання для показу може бути AsNoTracking; мутації виконуються лише на tracked
  агрегаті. Домен не залежить від EF і не може автоматично прикріпити detached-граф.
- Навіть паралельні правки різних вимірів однієї серії конфліктують за Version
  агрегату. Z2/Z4 повинні перечитати дані й перевірити стан; сліпого retry підпису немає.
- MeasuredAt може описувати історичні/імпортовані дані. Перевіряється UTC, але не
  вводиться непогоджена заборона часу раніше CreatedAt. Серверний час підпису
  та часову політику задає сервіс; довільний час від клієнта не вважати довіреним.
- LegacyOwnerId=0 не доводить ані існування власника, ані давність запису: 0
  можливий і у старій схемі, і в новому записі. Права з нього не виводяться.
- Міграції застосовувати без конкурентних записувачів, з резервною копією.
  CLI SQLite попереджає про нетранзакційний PRAGMA foreign_keys під час rebuild:
  аварійне переривання не гарантує атомарного відкату всієї зміни схеми.
- Після review: build 0 warnings / 0 errors; 177 passed із PostgreSQL, 0 failed,
  0 skipped; без PostgreSQL 167 passed, 10 штатних skips. Аналізатори - exit 0.
- Чинний coverage-summary.py показує 96.89% ядра, поріг 80% пройдено. Він не
  зливає короткі шляхи Domain-тестів з assembly-prefixed шляхами інших звітів.
  Незалежний діагностичний перерахунок за assembly/file/line дає 481/483=99.59%.
  Скрипт і поріг не змінено; виправлення скрипту передається власнику Z2 (#7).
