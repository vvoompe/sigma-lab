# Приймальні кейси

Фіксований список кейсів, за яким оцінюється функціональна коректність продукту. Список
**затверджується на ЧП1** і далі не змінюється без домовленості з викладачем.

Правила:
- кожен кейс має бути **автоматизованим** тестом (бажано) або відтворюваним скриптом;
- у колонці «Стан» ставиться `✅` лише тоді, коли кейс проходить у CI;
- зміна очікуваної поведінки - це зміна контракту: issue + PR + позначка в описі PR для всієї команди.

## Коди відповідей на доступ до чужих ресурсів (зафіксовано)

Єдине рішення для всієї системи, щоб клієнт поводився передбачувано:

- **404** - читання ресурсу, якого немає **або** який належить іншому користувачу: існування
  чужого ресурсу не розкриваємо;
- **403** - спроба **зміни** ресурсу, який існує, але прав на дію немає;
- **409** - ресурс доступний, але дія конфліктує з його станом (підписана серія, дубль).

Це рішення продубльовано в `docs/ARCHITECTURE.md`, розділ 7.

## Мінімум для ЧП1

**Кейси 8 і 9** перевіряються тестами `SiteServiceTests`; `SitesApiTests` додатково
перевіряє HTTP-створення 201 з Location та читання створеного майданчика.

Кейси **21 і 22** реалізовано для наявного ресурсу Site у першій частині #6.
`pageSize` понад 100 обмежується без помилки, далека сторінка повертає 200 і порожній
`items`. Друга частина #6 додає таку саму поведінку для приладів, серій і вимірів.
Очікування кейсів не змінювалися.

### Автоматизація другої частини #6

Статуси цих кейсів залишено без нових позначок до проходження CI цього PR.
Кейс 14 стосується окремого sync endpoint: звичайний POST виміру на дубль дає 409.
Підпис через HTTP (19), зміна окремого виміру (20), sync і експорт цим PR не заявлені.

### Перевірка Z3, issue #8

Кейси 5 і 6 пройшли CI у [PR #27](https://github.com/vvoompe/sigma-lab/pull/27):
усі п'ять перевірок успішні. Локальні `AuthApiTests` перевіряють реєстрацію,
дубль email, однакове тіло 401 для хибного пароля й невідомого email, lockout
після п'яти спроб, заборону самозміни ролі та аудит адміністративної зміни.
Кейси 1–4 залишаються без `✅`, доки їх не підтвердить CI credentials PR.
Для Site додано локальні HTTP-тести власності: чужий майданчик не повертається у списку
й дає 404 на читанні та 403 на зміні. Локальні `ResourceApiTests` також перевіряють
кейс 7 для чужого читання та кейс 19 для доступного LabManager: підпис встановлює
серверні `SignedAt`/`SignedById` і створює `experiment.signed`. Позначка стану очікує CI.

Для чистої бази `Seed__AdminEmail` і `Seed__AdminPassword` створюють першого
Administrator під час старту API. Якщо адміністратор уже існує або змінні не задані,
сідування нічого не змінює; пароль не записується в журнал і зберігається лише як хеш.
який залишається очікувати сервісного/API контракту серій та CI.

HTTP-частину кейсу 24 оформлено в #51: GET /api/experiments/{id}/export.csv,
200 text/csv UTF-8 із кирилицею та правами читання серії. ExperimentExportApiTests
перевіряє Unicode, інваріантні числа/UTC, CSV quoting, формули, порожню й підписану
серію, 401/404 та OpenAPI. Це окремий endpoint Z2, не Worker-експорт Z4.
### Автоматизація Z4, #9 / #14 / #15

`ClientApiIntegrationTests` перевіряє клієнтський цикл через справжній API:
кеш серій у спільній SQLite, 50 команд із UUID, повтор без дублів та статистику.
Окремий сценарій із реальною PostgreSQL імітує втрату відповіді після commit,
включно з точністю UTC-часу. Тест ViewModel перевіряє відновлення без мережі,
офлайн-додавання, спливлий токен та очищення екрана при виході.
`MeasurementSynchronizerTests` перевіряє конфлікти версій/payload, cancellation,
явне перебазування й відкидання невдалої команди. `ExperimentCacheAndWorkerTests`
перевіряє міграції, відкат кешу, заборону змін підписаної серії, ідемпотентність
перерахунку, Unicode CSV/JSON і чистку.

Це не змінює очікувань кейсів 14–15: серверні 200/duplicate=true та HTTP 207 ще
потребують #45 (Z2). Послідовний клієнтський транспорт не позначається як виконаний
пакетний endpoint. Worker експортує файли; HTTP-експорт кейсу 24 залишається Z2.
Позначки ✅ для цих трьох кейсів цим описом не додаються.
Серверний контракт кейсів 14–15 підготовлено окремо у #45: одиничний sync повертає
200/duplicate=true на ідентичний повтор, пакет до 50 — HTTP 207 із незалежними
результатами. Перевірки: MeasurementSyncApiTests (HTTP, SQLite та PostgreSQL).
Повне виконання кейсів офлайн-клієнта потребує review й підключення транспорту Z4;
сам серверний PR не закриває umbrella #14.

### Інтеграція Z4 після review, #14 / #53

Клієнт підключено до single/batch #49. MeasurementSynchronizerTests перевіряє
один реальний за формою 50-item запит, HTTP 207, partial failure, втрату відповіді,
порядок/повноту UUID та відповідність payload; помилка не стає Sent.
ClientApiIntegrationTests виконує синхронізацію через TestServer; PostgreSQL
перевіряє повтор після втрати single-відповіді й усього пакета з 50 записів.
ManagerContextIntegrationTests перевіряє дозволений контекст, справжнього
власника/еталон, офлайн-кеш та заборону мутацій менеджером на SQLite/PostgreSQL.
Позначки приймання залежать від CI фінального head та незалежного review,
а наскрізний Windows/Android показ залишається окремою runtime-перевіркою.
