# Клієнт MAUI — зона Z4

Windows і Android, MVVM без додаткового UI-фреймворка. Сторінка передає дії
`LaboratoryViewModel`; мережеві запити виконує `LabApiClient` через спільні DTO.
Доменних копій `Experiment`, `Measurement`, `Instrument` немає.

## Підготовка та запуск

Потрібні .NET SDK 10, MAUI workloads .NET 10, Android SDK API 36 / build-tools 36.0.0,
JDK 21. Сервер потрібен для першого входу та завантаження даних. Прилади досліднику
призначає адміністратор; серверне створення першого адміністратора відстежується в #40.

```powershell
dotnet workload install maui-windows maui-android
dotnet build src/Lab.Client.Maui/Lab.Client.Maui.csproj -c Release -f net10.0-windows10.0.19041.0
dotnet build src/Lab.Client.Maui/Lab.Client.Maui.csproj -c Release -f net10.0-android
dotnet run --project src/Lab.Client.Maui/Lab.Client.Maui.csproj -f net10.0-windows10.0.19041.0
```

На Android встановіть APK на пристрій або запустіть проєкт з Visual Studio на AVD.
Адреса сервера — HTTPS origin, наприклад `https://lab.example.org`, без `/api`.
Сертифікат мусить бути довіреним на пристрої. Для емулятора `localhost` означає
сам емулятор; потрібна доступна йому адреса сервера та відповідний сертифікат.
Валідація TLS не вимикається. Пароль не зберігається; токен і профіль — у MAUI SecureStorage.
Android backup вимкнений, щоб не переносити захищені дані між інсталяціями.

Перед запуском клієнта приберіть серверне `LAB_DB_PROVIDER=Postgres`, якщо воно задане.
Клієнт відхиляє таку конфігурацію, щоб не відкрити серверну БД замість локальної SQLite.

## Сценарій користувача

1. Вкажіть HTTPS-адресу, email і пароль; натисніть вхід. Завантажуються всі сторінки
   доступних майданчиків, приладів і серій. До успішного завершення завантаження
   попередній кеш не замінюється.
2. Оберіть серію зі SQLite. Нову серію можна створити онлайн, обравши майданчик,
   прилад і назву. Призначення приладів/майданчиків належить серверним ролям.
3. Без мережі введіть вимір. Спільний домен перевірить стан чернетки й діапазон.
   Команда з UUID та UTC-часом збережеться у файловий журнал, що є джерелом
   невідправлених операцій. Вимір ще не є підтвердженим записом серверної БД.
4. Після повернення мережі натисніть синхронізацію. Порядок операцій зберігається
   незалежно від переведення годинника. Стан і причина помилки доступні на екрані.
5. Для статистики оберіть серію й натисніть відповідну кнопку. Розрахунок повертає
   серверне математичне ядро, включно зі СКО, похибкою та довірчим інтервалом.

Після перезапуску можна читати серії та додавати виміри навіть зі спливлим токеном.
Для мережевих дій потрібен повторний вхід. Кеш і черга ізольовані за HTTPS origin та
UserId; вихід очищає екран і захищену сесію, але зберігає чергу для наступного входу
того самого користувача. Локальна SQLite використовує `LabDbContext` та спільні
Fluent-конфігурації / міграції. Кеш містить потрібні для списку та валідації дані;
еталони й профілі автентифікації не копіюються. Статистика з еталоном читається з API.

## Ідемпотентність і конфлікти

- UUID генерується на пристрої один раз і повторно використовується при всіх спробах. UTC-час перед першим записом нормалізується до мікросекунд PostgreSQL, щоб повтор після читання БД мав той самий payload.
- Перед POST клієнт перевіряє серверні виміри за ClientId. Збіг UUID, значення й часу
  означає, що попередню спробу вже підтвердив сервер. Інший payload — конфлікт.
- Якщо відповідь після commit втрачена, запис лишається Failed. Повтор з тим самим
  UUID розпізнає вже збережений вимір і переводить операцію в Sent без нового POST.
- Очікувана версія першої команди дорівнює кешованій версії серії; наступні локальні
  команди враховують попередні невідправлені додавання. На сервері версія перевіряється
  повторно. При конфлікті решта операцій цієї серії не відправляється.
- Кнопка повтору зберігає стару версію. Кнопка вирішення конфлікту після підтвердження
  користувачем читає поточну версію чернетки та змінює лише очікувану версію команди.
  UUID і вимір залишаються незмінними; підписана серія не перезаписується. Користувач також може явно відкинути невдалу локальну команду після підтвердження; наступні команди не перебазовуються мовчки.
- Зберігання JSON використовує тимчасовий файл і заміну. SemaphoreSlim працює лише
  в межах процесу; це не міжпроцесне блокування та не гарантія проти збою живлення.

Наявний API не має пакетного sync endpoint. Зараз 50 операцій передаються послідовно
через звичайний POST зі звітом клієнта. Це **не** HTTP 207 і не реалізація серверного
`duplicate=true`. Контракт і серверні критерії #14 / кейсів 14–15 винесені в #45 (Z2).
Клієнт не додає власного непогодженого сервера чи DTO в чужій зоні.

## Тести й CI

```powershell
dotnet build LabStem.Server.slnf -c Release
dotnet test LabStem.Server.slnf -c Release
```

Без `LAB_TEST_POSTGRES=1` PostgreSQL-сценарії пропускаються. Повний прогін потребує
окремої тестової БД та `LAB_TEST_POSTGRES_CONNECTION`; тести змінюють її дані.
Для coverage потрібен свіжий `TestResults` без XML попередніх прогонів:

```powershell
dotnet test LabStem.Server.slnf -c Release --collect:"XPlat Code Coverage" --results-directory TestResults
python scripts/coverage-summary.py
```

Серверні тести компілюють ті самі вихідні файли клієнтських сервісів, без MAUI UI.
`ClientApiIntegrationTests` проводить 50 вимірів через справжній API в TestServer,
перевіряє повтор без дублів і статистику; окремо перевіряє офлайн-відновлення ViewModel.
`MeasurementSynchronizerTests` імітує втрату відповіді після commit, конфлікти,
скасування й повторний UUID з іншим payload. `ExperimentCacheAndWorkerTests`
перевіряє спільні міграції, відкат неповного завантаження й експорт.
Ці перевірки не замінюють приймання інтерфейсу на Android/Windows.

Клієнт входить у `LabStem.slnx`; серверний `LabStem.Server.slnf` виключає лише MAUI.
CI `maui-build` збирає Windows і Android при зміні клієнта або його залежностей.
