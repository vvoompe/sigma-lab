# Лог інженерних рішень

Формат запису: **проблема → як виявили → рішення → що це дало**. Мета - не переказ роботи, а
відтворюваність: щоб наступна людина бачила причину рішення й команду, якою його перевірили.
Записів має бути не менше п'яти; реально їх буде більше.

## 1. Фіксація SDK: `version` 10.0.100 + `rollForward`

**Проблема.** У команди різні машини, і на кожній може стояти інша збірка SDK у межах 10.0.x.
Точна версія в `global.json` (наприклад `10.0.401`) означає, що в колеги з `10.0.300` збірка
впаде з помилкою «потрібен SDK 10.0.401», хоча компілятор і мова ті самі.

**Рішення.** У `global.json` вказано `"version": "10.0.100"` разом із
`"rollForward": "latestFeature"`. Це означає: підійде будь-який SDK 10.0.x із feature band не
нижче 100, включно з новішими. При цьому major-версія не «пливе»: SDK 11 або 12 не підхопиться.

**Що це дало.** Проєкт збирається однаково в усіх чотирьох учасників, і стек відповідає
платформі, зафіксованій у матеріалах курсу (.NET 10 LTS).

**Перевірка.** `dotnet --version` у корені репозиторію.

## 2. Два набори міграцій конкурують за `ModelSnapshot`

**Проблема.** Спроба тримати міграції для SQLite і PostgreSQL в одному проєкті призводить до
того, що друга міграція не бачить змін першої: знімок моделі один на набір, а DDL різний.

**Рішення.** Окремі проєкти `Lab.Migrations.Sqlite` і `Lab.Migrations.Postgres`, кожен зі своєю
`*DesignTimeDbContextFactory`, яка жорстко задає провайдера й власну assembly міграцій.
`Lab.Infrastructure` знає назви цих assembly лише рядками (`GetMigrationsAssembly`), тому
залежність іде тільки в один бік.

**Що це дало.** Застосувати «не той» набір міграцій неможливо випадково, а `dotnet ef` у
проєктах міграцій працює без `--startup-project` і без `--context`.

**Перевірка.** `dotnet ef migrations list --project src/Lab.Migrations.Sqlite` і те саме для
Postgres: набори незалежні, назви міграцій можуть відрізнятися за часовою міткою.

## 3. Аналізатори валили збірку на згенерованих міграціях

**Проблема.** У `Directory.Build.props` стоїть `TreatWarningsAsErrors=true` - вимога нуля
попереджень. Але код міграцій генерує EF Core, і він не відповідає вимогам стилю: зокрема
правило CA1861 спрацьовує на масивах-аргументах у конфігураціях індексів.

**Рішення.** Зауваження не вимикаються на рівні всього solution. У проєктах міграцій окремо
вказано `TreatWarningsAsErrors=false` і `<NoWarn>$(NoWarn);CA1861</NoWarn>` - тобто послаблення
стосується рівно генерованого коду, а не власного.

**Що це дало.** Збірка solution без попереджень, і при цьому власний код залишається під
найсуворішим режимом; вимога до якості виконується чесно.

**Перевірка.** `dotnet build LabStem.slnx -c Release` → `0 Warning(s) 0 Error(s)`.

## 4. Логування без зауважень аналізатора

**Проблема.** Звичайні виклики `logger.LogInformation("...", value)` у режимі
`AnalysisLevel=latest-recommended` дають зауваження (CA1848, CA1873): аналізатори вимагають
згенерованих делегатів журналювання.

**Рішення.** У `DatabaseStartup` і `SyncWorker` повідомлення описані атрибутом
`[LoggerMessage]` на `partial`-методах: генератор створює ефективний код, а попереджень немає.

**Що це дало.** Логи лишились читабельними, збірка лишилась чистою, а формат повідомлень став
однаковим у всьому проєкті - нові місця логування просто копіюють цей патерн.

**Перевірка.** Та сама збірка Release без попереджень.

## 5. Тести проти PostgreSQL не мають падати на машині без Docker

**Проблема.** Частина команди працює без піднятої PostgreSQL, і `dotnet test` не повинен через
це червоніти - інакше тести почнуть «вимикати» замість того, щоб читати їх.

**Рішення.** `Lab.Postgres.Tests` перевіряють змінну `LAB_TEST_POSTGRES` і за її відсутності
викликають `Assert.SkipUnless(...)`. У CI ця змінна виставлена, а `postgres:15` піднятий як
сервіс, тому там тести виконуються по-справжньому.

**Що це дало.** Локально `dotnet test` працює без Docker і чесно показує пропущені тести;
у CI - жодного пропущеного.

**Перевірка.** Два прогони: без змінної (є пропущені) і з нею (0 пропущених).

## 6. SQLite повертає `DateTime` без позначки UTC

**Проблема.** Під час перевірки запуску API виявилось: запис, збережений як
`2026-09-29T10:56:49.9514387Z`, читається назад як `2026-09-29T10:56:49.9514387` - **без `Z`**.
Причина не в нашому коді: SQLite не має окремого типу для дати, значення зберігається текстом,
і позначка UTC (`DateTimeKind.Utc`) при читанні губиться. PostgreSQL з `timestamp with time zone`
такої проблеми не має - там тип колонки зберігає зсув.

**Що це означає на практиці.** Домен скрізь працює з `DateTime` в UTC, але клієнт може отримати
дату без позначки зсуву й інтерпретувати її як локальну. Для польової лабораторії це критично:
виміри мають точний час, а різниця в кілька годин ламає зіставлення серій.

**Рішення (зафіксоване, доробляється зоною Z1).** Дати назовні віддаються в явному форматі ISO
8601 з `Z`, а не «як є»; для цього в контрактах достатньо серіалізувати `DateTime` із
`DateTimeKind.Utc` (`DateTime.SpecifyKind(value, DateTimeKind.Utc)` або `DateTimeOffset` у
контракті). Вибір варіанта - окреме issue зони Z1: просте `SpecifyKind` на читанні або
`DateTimeOffset` у DTO, з тестом round-trip на обох СУБД.

**Що це дало вже зараз.** Відмінність зафіксована документально, а не виявлена на захисті:
це саме той клас питань, які задають, коли чують «працює і на SQLite, і на PostgreSQL».

**Перевірка.** Прогін API на SQLite: `POST /api/sites` → `createdAt` із `Z`; `GET /api/sites`
після перезапуску контексту → `createdAt` без `Z`.

## 7. `.gitignore` із `*.sqlite` виключив цілий проєкт міграцій

**Проблема.** Після першого push у GitHub CI упав на кроці `dotnet restore`:
`The project file ".../src/Lab.Migrations.Sqlite/Lab.Migrations.Sqlite.csproj" was not found`,
хоча локально solution збирався й тести проходили.

**Як виявили.** `git check-ignore -v src/Lab.Migrations.Sqlite/Lab.Migrations.Sqlite.csproj`
показав `.gitignore:14:*.sqlite`. На Windows `core.ignorecase = true`, тому шаблон `*.sqlite`
(який мав закривати лише локальні файли бази) збігається з **каталогом**
`src/Lab.Migrations.Sqlite` і виключає його повністю. `git ls-files | grep Migrations.Sqlite`
повертав 0 файлів - тобто в репозиторії проєкту не було взагалі.

**Рішення.** Шаблон `*.sqlite` прибрано, лишились явні `*.sqlite3` і `*.sqlite-journal`.
У `.gitignore` додано попередження, щоб шаблон не повернули випадково. Файли проєкту
додано в репозиторій і перевішено через CI.

**Що це дало.** CI знову зелений, і з'явилось правило перевірки: якщо «локально працює,
а на CI файлів немає» - перша команда `git check-ignore -v <шлях>`, а не пошук проблеми
в коді. Це загальний клас пасток: локальна збірка читає файли з диска, а не з git.

**Перевірка.** `git ls-files | grep -c Migrations.Sqlite` більше нуля і зелений прогін CI
на гілці `main`.

## 8. Клієнтська черга без дублювання доменної моделі

**Проблема.** Issue #9 вимагає спільну доменну модель. У main ще немає Experiment,
а незалежна частина клієнта вже потребує надійного збереження офлайн-операцій.

**Рішення.** Локальні доменні дані читаються через наявний LabDbContext і міграції
Lab.Migrations.Sqlite. Черга зберігає лише транспортну операцію: UUID, тип та ідентифікатор
ресурсу, JSON payload, стан Pending / Sent / Failed, час і історію спроб. Це окремий
атомарно замінюваний файл у приватному каталозі застосунку. Доступ синхронізовано між
екземплярами сервісу в одному процесі; запис спершу завершується у файлі з унікальним
тимчасовим ім'ям, після чого він замінює попередній знімок.

**Що це дало.** Клієнт не оголошує власний Experiment і не змінює схему Z1. Повторне
додавання одного UUID повертає наявну операцію. Помилкова операція зберігає причину й
повертається в Pending для повторної спроби. Пошкоджений файл не перезаписується.
Серверне відправлення та політика конфліктів залишаються предметом issue #14.

**Перевірка.** SyncQueueStoreTests перевіряє порожню чергу, ідемпотентність після
повторного відкриття, паралельні записи, пошкоджений файл і переходи станів.
LocalDatabaseServiceTests застосовує спільні міграції SQLite та читає збережений Site.

## 9. Ізоляція SQLite та відкату міграцій

**Проблема.** CI виставляє `LAB_DB_PROVIDER=Postgres`, і ця змінна за контрактом має
вищий пріоритет за конфігурацію. Через це сценарій локальної SQLite вибирав PostgreSQL
та падав до відкриття бази. Додатково застосування міграцій перевіряло лише прямий напрямок;
відкат і фабрики `dotnet ef` залишались неперевіреними.

**Рішення.** SQLite-тест явно виставляє потрібного провайдера на час сценарію й відновлює
попереднє значення у finally. Сценарії зі змінними середовища належать колекції з вимкненим
паралельним запуском. Тести фабрик перевіряють специфічний рядок підключення, спільну змінну,
значення за замовчуванням, провайдера й відповідний набір міграцій. Сценарій міграцій застосовує
схему, зберігає дані, відкочує до нуля, перевіряє відсутність таблиці та відтворює порожню схему.
Для PostgreSQL створюється окрема база `sigma_migration_<UUID>`; видаляється лише ця база.

**Що це дало.** Один прогін перевіряє обидва провайдери без конфліктів середовища. Відкат
не торкається спільної тестової бази або локальних даних. Прогалини закриваються виконанням
реальних сценаріїв; виключення файлів і формула звіту покриття не змінювались.

**Перевірка.** `MigrationFactoryTests`, `MigrationLifecycleTests` та
`LocalDatabaseServiceTests`; прогін із `LAB_TEST_POSTGRES=1` і реальною PostgreSQL.

## 10. Незалежне математичне ядро Z1

**Проблема.** Issue #5 потребує перевірених розрахунків, але модель User та її зв'язки
ще потребують узгодження з Z3. Підміна цього контракту випадковою моделлю створила б
несумісні міграції. Математика не залежить від схеми й може бути завершеним інкрементом.

**Рішення.** Чисті функції в `Lab.Application/Statistics` (за місцем розрахункового ядра
у структурі проєкту), без DTO/контролерів/DbContext. Вибіркове СКО з n-1, стандартна
похибка, t-інтервал середнього, мітки 3σ без видалення, абсолютний допуск зі збігом
одиниць, лінійна МНК-апроксимація з центрованим прогнозом. MathNet.Numerics 5.0.0 (MIT)
використовується тільки для StudentT.InvCDF замість власної інверсії розподілу.

**Межі.** Немає автоматичної конвертації одиниць, перевірки нормальності чи гарантій
екстраполяції. Неприпустимі/непредставні обчислення відхиляються явно. Припущення,
формули, чисельна похибка й семантика RMS/R² - у [statistics-core.md](statistics-core.md).
HTTP-кейси не позначені виконаними за самими математичними тестами.

**Перевірка.** Цільові тести до/після реалізації й регресія всієї solution з окремою
PostgreSQL 15; чисельні дефекти відтворюються тестами до виправлення. Issue #3/#4,
реєстрація, права, API й клієнт залишаються окремими задачами.

## 11. Модель Z1 та безпечний перехід до User

**Проблема.** Issue #3/#4 потребують повної моделі на двох СУБД. Старий OwnerId
був довільним int без User; пряме додавання FK зламало б існуючі дані або вимагало
фіктивних користувачів. Окремо треба не дозволити конкурентний запис у підписану серію.

**Рішення.** Саша погодив User як мінімальний профіль з int Id, email та іменем,
без реалізації auth Z3. Одна серія використовує один прилад та його одиницю.
NormalizedEmail матеріалізований для переносимої UNIQUE-перевірки; інші метрологічні
поля не дублюються у вимірах. Version серії й виміру - app-managed concurrency tokens,
ClientId - глобальний UNIQUE UUID. Один SaveChanges атомарно зберігає зміни агрегату.
LegacyOwnerId зберігає старе значення, новий nullable OwnerId посилається лише на реальний User.
Автоматичного зіставлення старих ідентифікаторів із новими акаунтами немає.

**Як виявили дефект.** Нові SQLite-тести пройшли, але повна регресія впала на Down:
EF відкладає перебудову sites до завершення операцій, а lab_users видалявся раніше.

**Виправлення.** DomainModel і SiteOwnership - окремі міграції в обох наборах.
Відкат SiteOwnership завершує зняття FK до видалення профілів у DomainModel.
Вихідні InitialCreate не змінено; ручного SQL DML немає.

**Перевірка.** Доменний кластер, SQLite persistence, реальна PostgreSQL 15;
upgrade/downgrade/upgrade старих Site, latest -> 0 -> latest, UUID rollback і гонка
зі старою версією після підпису. Межі API/auth/sync та правила downgrade описано
в [data-model.md](data-model.md). Згода Саші ще не заміняє командне review Z2/Z3/Z4.

**Після незалежного review.** Додано регресійний тест втрати UTC у Site.CreatedAt:
до виправлення Utc != Unspecified, після HasConversion тест проходить на SQLite;
PostgreSQL також перевірено. Збереження редагованого виміру й обох Version та
відкат непорожнього агрегату додатково перевірено на двох СУБД. Остаточно:
177 passed, 0 failed, 0 skipped із PostgreSQL, Release build 0/0, analyzers exit 0.
Виявлено окрему проблему злиття коротких шляхів у coverage-summary.py; поріг
проходить і без його зміни, виправлення скрипту залишається Z2 (#7).

## 12. Обмежена вибірка майданчиків у Z2

**Проблема.** `GET /api/sites` повертав усі записи одним масивом. Для першого етапу #6
потрібні фільтри й пагінація на наявному Site без створення моделей зони Z1.

**Рішення.** `SiteQuery` задає сторінку, фрагмент назви та включні межі координат.
`PagedResult<SiteDto>` повертає `items`, кількість після фільтрів і фактичні параметри
сторінки. `pageSize` понад 100 обмежується до 100 відповідно до кейсу 21; некоректні
значення відхиляються. Порядок за назвою та Id стабільний для незмінного набору даних,
зміщення рахується як long. Валідація працює і в HTTP, і при прямому виклику сервісу.

**Вплив.** Публічний контракт списку змінено з масиву на сторінку, потрібне рев'ю Z4.
Схема БД і локальний клієнт не змінюються. Докладна семантика — у `docs/api-sites.md`.

**Перевірка.** SQLite-тести сервісу, HTTP-тести в ізольованому застосунку, перевірка
згенерованого OpenAPI й загальний прогін із PostgreSQL. Поріг покриття окремо
перевіряється запуском CLI на штучних звітах нижче 80%, на межі та без даних.

## 13. Достовірність coverage та підсумковий CI gate (Z2, #30)

**Проблема.** Coverlet записує один файл коротким і повним шляхом. Старий ключ
`(filename, line)` дублював рядки, а пошук підрядка в шляху неправильно визначав ядро.

**Рішення.** Ключ — `(assembly, нормалізований шлях усередині assembly, line)`, злиття
через max hits, включно з нульовими рядками. Склад ядра явно незмінний: Domain,
Application, Infrastructure; поріг 80%. Невизначена assembly — помилка звіту.

**CI.** Додано `ci-gate` з `always()` після сервера, матриці SDK, фільтра шляхів і MAUI.
Штатний skip MAUI приймається лише для нерелевантних змін. Власник має окремо зробити
цей check обов'язковим, зберігши наявні required checks; DiXer-code не має admin.

**Перевірка.** Чотири нові регресійні тести відтворили дефект старого скрипту.
Після виправлення 21 Python-тест проходить. Release build: 0 warnings, 0 errors;
.NET: 63 + 135 + 28 = 226 passed, 0 failed, 0 skipped, PostgreSQL 15 в окремій базі.
Три свіжі XML: ядро 512/514 (99.61%); два непокриті рядки лишилися у знаменнику.

**Відтворюваність.** Локальний tool manifest фіксує dotnet-ef 10.0.12, як EF Core у
проєктах міграцій. README розділяє Bash/PowerShell, сервер/MAUI та вимагає свіжі звіти.
PR #29 залишається на базі feature/8-user-credentials і не входить у завершення ЧП1.

## 14. JWT-контракт першого етапу Z3

**Проблема.** Issue #8 починається з Bearer-перевірки та негативних кейсів 401/403,
але ще не має сервісу видачі токенів. Водночас API вже має endpoint-и Z2, які не можна
переписувати зони Z3 без узгодження.

**Рішення.** Перевіряти лише підписані HS256 JWT з обов'язковими `exp`, визначеними
issuer/audience та нульовим `ClockSkew`. Ключ читається тільки зі змінної середовища
`Jwt__Key`, має бути не коротшим за 32 UTF-8 байти, а відсутність/некоректність ключа
зупиняє конфігурацію API. Fallback-політика вимагає аутентифікацію й одну з трьох
підтримуваних ролей, тому Z2 endpoint-и захищені без атрибутних змін їх контролерів;
окремі політики ролей зареєстровані для майбутнього застосування на операціях. OpenAPI
описує глобальну Bearer-схему, щоб документація збігалася з реальною вимогою токена.

**Що це дало.** Новий `ICurrentUser` читає int `sub` і роль лише з верифікованого principal.
Тіла запиту, `LegacyOwnerId` і недовірені claim-и не створюють поточного користувача.
Реєстрація/вхід, зміна ролей з аудитом та прив'язка власника до ресурсу реалізуються
окремими частинами #8; аудит підпису серії також очікує реалізації.

**Перевірка.** HTTP-тести перевіряють відсутній токен (401), хибний підпис (401),
непідтримувану роль (403), OpenAPI Bearer-схему, коректну автентифікацію та розбір
`ICurrentUser`.

## 14. Облікові дані, lockout і аудит Z3

**Проблема.** Issue #8 потребує реєстрації й входу без перенесення пароля/ролі до
профілю Z1, однакової відповіді для невідомого email і хибного пароля, обмеження
повторних спроб, адміністрування ролей та аудиту.

**Рішення.** `UserCredential` має спільний PK/FK із `User`; ASP.NET
`PasswordHasher<UserCredential>` зберігає тільки хеш. Реєстрація задає роль
`Researcher` незалежно від тіла запиту; прийнята парольна політика — 12–128 символів
без вимог до класів символів. П'ять невдалих спроб блокують вхід на 15 хвилин.
Для невідомої адреси перевіряється dummy-хеш, а відмови входу мають однаковий
401 ProblemDetails без динамічного `traceId`. Access token HS256 чинний 30 хвилин.

Зміна ролі доступна тільки Administrator через `PATCH /api/admin/users/{id}/role`;
власну роль змінити не можна. Зміна credentials і `AuditEntry` зберігаються одним
`SaveChangesAsync`, а унікальний індекс `NormalizedEmail` захищає від конкурентних
реєстрацій; конфлікт, підтверджений повторним пошуком, повертається як 409.
Схема викладена окремими міграціями `SecurityCredentials` для SQLite та PostgreSQL
з незалежними snapshots.

**Вплив.** Профіль `User` і його поля не змінюються. Контракти реєстрації, входу та
зміни ролі належать Z2 і потребують його рев'ю; схема й міграції потребують рев'ю Z1.
Видача токенів спирається на попередній JWT-контракт Z3.

**Перевірка.** `AuthApiTests` перевіряє реєстрацію без витоку хешу, дубль email,
401 із однаковим тілом, п'ять помилок і 15-хвилинне блокування, зміну/самозміну ролі,
аудит та публічність auth endpoint-ів в OpenAPI. SQLite-міграція застосовується в тесті,
який перевіряє shared PK/FK, UTC, аудит і повторний запуск; snapshots обох СУБД не мають
pending model changes. `dotnet build LabStem.Server.slnf -c Release` — 0 попереджень/
помилок; `dotnet test LabStem.Server.slnf -c Release` — 242 пройшло, 10 пропущено.
PostgreSQL-тести не виконалися: сервер на localhost:55432 недоступний, тому міграцію
Postgres згенеровано й перевірено за моделлю, але не застосовано до живої БД.

## 15. Перевірка власності майданчика

**Проблема.** Токен підтверджує особу, але без сервісної перевірки власності список,
читання й оновлення Site можуть показати або змінити дані іншого користувача.

**Рішення.** Створення записує власника з перевіреного `ICurrentUser.Id`; список і
читання фільтруються за ним, а чужий/legacy Site не розкривається на читанні (404).
Сервіс розрізняє відсутній запис (404) та наявний чужий (403) при
`PUT /api/sites/{id}`. Оновлення міняє лише назву й координати, не власника/дату створення.
Authorization policies також відхиляють токен без додатного числового `sub`.

**Вплив.** Дані й схема БД не змінюються. Новий `UpdateSiteRequest` і `PUT` — зміна
контракту Z2; потрібне їхнє рев'ю перед PR merge.

**Перевірка.** `SitesApiTests` перевіряє власне створення/оновлення, 404 на читання
чужого Site, 403 на його зміну й відсутність чужого запису у списку; сервісні тести
також перевіряють розділення доступу. `dotnet build LabStem.Server.slnf -c Release` —
0 попереджень і помилок; `dotnet test LabStem.Server.slnf -c Release` — 245 пройшло,
0 падінь, 10 штатних пропусків PostgreSQL. Тести виконано локально без живої PostgreSQL.
Кореневі `dotnet build -c Release` і `dotnet test` заблоковані відсутньою workload
`maui-android` (NETSDK1147).

## 16. Z2: повний PUT Site та передача контракту серій Z3

18.10.2026, #6 / #8. Review `feature/8-user-credentials` (`172ccbb`).

**Проблема.** JSON PUT без координати перетворював її на default(double)=0 і
повертав 204; для повного оновлення це прихована втрата попередніх даних. 403 через
Forbid не мав тіла, хоча OpenAPI декларував ProblemDetails. Назва, невалідна після

**Рішення Z2.** Обидві координати nullable в DTO з Required/Range: відсутнє/null

до мутації; IValidatableObject перевіряє довжину назви після Trim. Контролер повертає
ProblemDetails для відмови у власності. OwnerId/CreatedAt і політики Z3 не змінюються.

**Доказ.** До виправлення 6 із 11 нових HTTP/OpenAPI-перевірок падали на неправильній
поведінці. Після виправлення й додавання 3 сервісних перевірок усі 14 пройшли.
Повна Release-збірка: 0 warnings/errors; 269 .NET-тестів із реальною PostgreSQL 15,
0 failed/skipped; 8 Python-тестів. HTTP-тести використовують TestServer і SQLite
зі справжніми міграціями; PostgreSQL-прогін перевіряє збереження/міграції окремо.

**Порядок інтеграції.** Власна гілка Z2 створена від явно переданої гілки Z3,
PR спрямований у `feature/8-user-credentials`, щоб не переносити чужу незлиту
реалізацію до main без review. Workflow тепер запускається й для PR у цю конкретну
гілку; перевірки main не змінено. Після review Z3 приймає цей PR, потім credentials
проходять окремий PR до main із review схеми Z1. Ця передача не закриває весь #8.

**Наступний етап.** [Контракт серій Z2/Z3](z2-z3-experiment-contract.md) описує DTO,

залишається явним питанням Z3/Z1; OwnerId/LegacyOwnerId не підміняють її.

## 17. API #6: агрегат серії, конфлікти та відтворювана статистика

**Проблема.** Після інтеграції моделі Z1 потрібні публічні контракти приладів,
серій, вимірів і статистики без обходу доменних інваріантів. Два одночасні запити
можуть пройти попередню перевірку Version, UUID чи FK, але конфліктувати при записі.

**Рішення.** DTO описують тільки дозволені операції: PUT перейменовує; метрологічні
параметри приладу незмінні. Сервіси працюють через IAppDbContext і tracked агрегат
із Instrument та повною Measurements для додавання. Кожна зміна серії перевіряє
очікувану Version; домен підвищує її, EF concurrency дає 409. Чужі серії приховані
на читанні та заборонені для зміни; відсутність призначення менеджера не відкриває
глобальний доступ. SignedOff захищено перед кожною мутацією.

Попередня перевірка дубля не замінює обмеження БД: після DbUpdateException сервіс
перевіряє відомий UUID/SerialNumber/FK-конфлікт. Інші збої лишаються безпечним 500,
їх не видаємо за успіх чи 409. Для видалення використовується існуюча AuditEntry
Z3 у тій самій транзакції SaveChanges, включно з відкатом при concurrency.

Статистика завантажує версію, Instrument, ReferenceValue та Measurements одним
AsSingleQuery, потім викликає незмінене ядро Z1 з одиницею серії. Для цього явно
додано EF Core Relational 10.0.12. 3σ лише позначає; допуск включний; нечислові
та непредставні результати відхиляються. Повний контракт — [api-resources.md](api-resources.md).

**Перевірка.** 46 нових HTTP/OpenAPI/конкурентних перевірок, зокрема дві на реальній
PostgreSQL. Повний прогін: 321 passed без пропусків; Release 0 warnings/errors;
21 Python-тест; ядро 952/968 = 98.35% (база PR #34: 97.89%). Поріг і фільтри
покриття не змінені. Чотири DbSet відкривають уже відображені сутності без міграцій;
їх рев'ю Z1 ведеться в #35. Гілка створена від main, credentials підключені звичайним
merge; інтеграційний PR спрямовується до ще не злитої гілки #34. Підпис та завершення
#8 — окрема робота Z3.
