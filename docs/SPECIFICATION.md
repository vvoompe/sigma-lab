## 1. Призначення системи

Система збору, математичної обробки та аналізу даних польових вимірювань. Дослідник вносить
виміри в мобільному застосунку **навіть без мережі**; після появи зв'язку дані синхронізуються
із сервером; система рахує статистику й похибки, тримає серії вимірювань і порівнює їх з еталоном.
Мета - прибрати паперовий журнал польових вимірювань і дати змогу аналізувати результати
відразу після повернення зі зв'язком.

## 2. Цільові користувачі та ролі

| Роль | Що може |
|---|---|
| Researcher | веде власні серії вимірювань, додає виміри, бачить статистику |
| LabManager | бачить усі серії свого майданчика, **підписує** серії після завершення |
| Administrator | керує користувачами, майданчиками й приладами |

## 3. Функціональні вимоги

- **FR-1.** Реєстрація та вхід із видачею токена; розмежування доступу за ролями.
- **FR-2.** Ведення майданчиків відбору (Site) з координатами.
- **FR-3.** Ведення приладів (Instrument) з одиницею та похибкою; серійний номер унікальний.
- **FR-4.** Серії вимірювань (Experiment) зі станами «чернетка» і «підписана».
- **FR-5.** Додавання вимірів (Measurement) із значенням, одиницею та часом; перевірка діапазону приладу.
- **FR-6.** Внесення вимірів офлайн і синхронізація з сервером без дублів.
- **FR-7.** Розрахунок статистики серії: середнє, СКО, стандартна похибка, довірчий інтервал.
- **FR-8.** Чисельні методи: лінійна регресія, апроксимація, виявлення викидів за правилом 3σ.
- **FR-9.** Порівняння серії з еталоном (ReferenceValue) у межах заданого допуску.
- **FR-10.** Підпис серії керівником із записом в аудит.
- **FR-11.** Експорт серії у CSV.
- **FR-12.** Пагінація, фільтрація та сортування колекцій.

## 4. Правила предметної області (інваріанти, їх перевіряють тести)

1. Вимір можна додати лише в серію зі станом «чернетка»; підписану серію не змінюють.
2. Значення виміру мусить бути в межах діапазону приладу - інакше 400 з поясненням.
3. Ідентифікатор виміру на пристрої унікальний: повторна синхронізація не створює дубль.
4. Розраховані статистики не зберігаються як «істина» - вони перераховуються (окрім кешу).

## 5. Нефункціональні вимоги

- **Мультиплатформність:** клієнт .NET MAUI працює щонайменше на Windows і Android з однієї кодової бази.
- **Незалежність від СУБД:** перемикання SQLite (офлайн-клієнт) / PostgreSQL (сервер) через конфігурацію.
- **Якість:** покриття тестами ядра ≥ 80 %, збірка без попереджень, нуль зауважень аналізатора.
- **Відтворюваність:** README, за яким проєкт запускається з нуля без втручання автора.
- **Безпека:** секрети поза репозиторієм, перевірка володіння ресурсом у сервісному шарі, аудит дій.

## 6. Склад системи та стек

- Функціональна коректність вимірюється фіксованим списком **24 приймальних кейсів**
  (`docs/acceptance-cases.md`), який затверджується на ЧП1. Мінімум для ЧП1 - кейси 8, 9, 21, 22
  (їх уже проходить каркас).

- README перевірено запуском на чистій машині.
- Процес: issue -> гілка -> PR -> рев'ю -> merge; лог рішень ≥ 5 записів; файл `META-USAGE`.
- Поріг зарахування проєкту - 60 %.
